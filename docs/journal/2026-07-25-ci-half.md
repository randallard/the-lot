Documents commits `b8ec634` and `782fc02`. Second entry today; the first was

The trailing half of the ADR-0002 retrofit, handed to this machine by the other one — and

## The handover was right, and that mattered

It arrived with measurements rather than estimates: 61 lint errors, 25 warnings, ~26 of them
`react-hooks/*`, `docs-hygiene.py` already clean, `ci.yml`'s `detect` job self-skipping the
Rust half. I re-ran all of it before touching anything. Every number was exact.

That bought real trust, and it's worth naming why: a handover that says "lint has some
problems" produces an hour of rediscovery. One that says "61 errors, here's the rule
breakdown, ~26 are architectural" lets the next machine start at the decision instead of the
survey.

## Where it was wrong, and the shape of the wrongness

Everything it missed was in the one job it hadn't run — `ts-supply-chain`:

- `pnpm audit` found **27 vulnerabilities, 15 high and 1 critical**. All devDependencies.
  `pnpm update` inside existing semver ranges cleared 26 of them.
- `license-checker-rseidelsohn` **wasn't installed at all**. The template has no
  `package.json`, so `pnpm exec license-checker-rseidelsohn` had never once run in anger.
- The license gate then failed on **`@react-three/rapier`, which publishes with no `license`
  field and no LICENSE file in the tarball**. Upstream is MIT; the package just doesn't say
  so.
- Four more licenses needed allowing, all permissive toolchain transitives.
- `pnpm/action-setup` had no version to resolve.
- pnpm 11 no longer reads `pnpm.*` from `package.json` — the handover's suggested
  `pnpm.onlyBuiltDependencies` fix was already stale. It lives in `pnpm-workspace.yaml` now.

The pattern is consistent: the handover was accurate about everything it had **executed**, and
wrong about everything it had only **read**. That's the same lesson as this morning's brief,
one level down. Predicting a gate is not running it.

## rapier: the license gate found the dead dependency

The nicest moment. `@react-three/rapier` had already been flagged in ADR-0001 as installed but
never imported — "physics was provisioned, not adopted." The license gate independently
tripped over the same package for an unrelated reason.

So the fix wasn't to except it. It was to delete it. A dependency that is unused *and*
undeclared as to license isn't a compliance problem to configure around; it's just gone. When
physics is genuinely wanted it comes back as a deliberate choice, and the license question gets
asked then rather than suppressed now.

## Refusing to override a supply-chain control

One advisory survived `pnpm update`: `brace-expansion` GHSA-mh99-v99m-4gvg, dev-only, reached
solely through eslint's own minimatch. The patch exists — 5.0.8 — and pnpm **refused to install
it**, because it was published two days ago and pnpm 11 enforces a 72-hour `minimumReleaseAge`
quarantine by default.

That's a genuinely interesting standoff: a supply-chain control blocking a supply-chain fix.
The quarantine exists to stop a compromised fresh publish from being pulled in automatically,
which is a materially larger risk than a denial-of-service in the linter's glob expander. So
the right move was to wait it out, not override it — an explicit single-advisory ignore with a
removal date, rather than `--audit-level=critical` or a forced override.

## The ninth gate

Local dry-runs of all eight gates passed. CI then failed on a ninth I hadn't known to run: the
**OSV scan**, a reusable workflow that can't be exercised from a local checkout.

It found exactly one vulnerability — the same `brace-expansion` — because osv-scanner reads its
own config file, not pnpm's. Two ignores for one advisory, in two tools, over two databases.
`osv-scanner.toml` at least supports `ignoreUntil`, so that gate re-arms itself on 2026-07-27
whether or not anyone remembers.

Worth recording as a general point: "I ran every gate locally" was true and still insufficient.
The reusable-workflow jobs are only observable in CI.

## The linter, the architecture, and knowing when to stop

The 61 lint errors resolved into three groups. 35 mechanical — fixed. 21 architectural —
`eslint-plugin-react-hooks` objecting to ADR-0002's shared-ref pattern on purpose, excepted by
path in ADR-0008 rather than repo-wide or per-line. And 5 ordinary React issues that were
neither, which I fixed instead of excepting — **and one of those was a real bug**:
`SettingsApp`'s `settingsActions` memoized on `[onOpenBodyEditor]` while closing over `prefs`,
so the keyboard shortcut for "toggle AI responses" was firing against stale preferences. The
linter earned its place in the gate before the gate even landed.

Then I nearly broke it. The audit-driven `pnpm update` had quietly bumped
`eslint-plugin-react-hooks` 7.0.1 → 7.1.1, and the full local run came back with **56 errors**
where minutes earlier there had been zero. 7.1.1 reclassifies most `immutability` findings as
`refs` — 6 becomes 47 — and extends them to `App.tsx`, which is fair, because `App.tsx` is
where every shared ref is created.

The temptation was to widen the exception list until it went green. But eight of the new errors
weren't the ref pattern at all; they needed real restructuring in the game-return handler and
the assembly-cutscene step machine — behaviour-critical paths, on a codebase I can't play-test
from here. Widening the exceptions to cover them would have been suppression dressed as
scoping.

So I pinned the plugin to exact `7.0.1`, measured what 7.1.1 costs, and wrote it down as its
own piece of work. Pinning a linter to avoid its findings is a smell; pinning one because an
incidental transitive bump changed the job description mid-change, with the delta measured and
scheduled, is sequencing. The difference is entirely in whether the number gets written down —
so it's written down, in ADR-0008 and worklist item 3.
